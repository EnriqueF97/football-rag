# Project Charter — Evaluation-First RAG (Football News)

This file is the **charter**: why this project exists for me, how we work together, and
what we expect to get out of it. It is intentionally about _purpose and method_, not the
technical plan.

- The technical plan and current progress live in `project_progress.md`.
- What the system _is_ lives in `README.md`.
- How to run things lives in `docs/commands.md`.

---

## 1. Who this is for

Enrique Favila. Software engineering background. I am building this to **learn**,
hands-on, the engineering behind production retrieval-augmented generation (RAG) systems
and — above all — how to **evaluate** them rigorously.

- Speak **Spanish** to me by default. All code, docs, and commits in **English**.
- I am an engineer: explain at a technical level, don't oversimplify, but don't assume I
  already know the RAG/IR-specific concepts — teach those as they come up.

## 2. What I want to learn (the real purpose)

The point of this project is the skills, not the artifact. By the end I want to genuinely understand — well enough to defend in an interview and reuse at work:

- **How RAG works end to end**, not as a framework wrapper: chunking, embeddings, vector
  stores, BM25, hybrid fusion, and cross-encoder reranking — and _why_ each exists.
- **How to evaluate an LLM system with rigor**: building a human-annotated golden set,
  measuring retrieval and generation _separately_, using an LLM judge that is itself
  validated against human annotation, a closed-book contamination baseline, and
  abstention ("I don't know").
- **Cost and latency profiling** of LLM systems — the number product teams ask first.
- **Enough LangChain / LangGraph** to orchestrate, used sparingly and knowingly (not as a
  black box I can't explain).
- **Good engineering habits**: a reproducible pipeline (`uv`, one-command eval) and a
  clean, readable git history.

If a tradeoff ever pits "more features" against "more rigorous evaluation," pick
evaluation. That is the whole thesis.

## 3. How we work together (this matters most)

We build this **together, step by step** — not you coding a whole notebook end to end
while I watch. The rhythm is:

1. **Discuss the design** of the next piece before writing it. Name the options and the
   tradeoffs; give a recommendation.
2. **I make the call.** Surface choices, don't railroad; the decisions are mine.
3. **Implement one small, reviewable piece** at a time.
4. **Explain what it does and why** after building it, so I actually understand the
   component before we move on.
5. **Move to the next piece.**

Also:

- **Teach, don't just deliver.** When you introduce a concept (recall@k, cross-encoder,
  MinHash…), explain it in plain terms the first time.
- **Small, readable commits.** Committing is _my_ job unless I ask you to do it.
- **All Python dependencies go through `uv`.** Never bare `pip`.
- **Keep `project_progress.md` current** — checkboxes and percentages — so I always see
  exactly where we are and what's next.
- **Report honestly.** If something failed or was skipped, say so with the evidence. Don't
  claim a step works until it's actually been run.

## 4. Goals — what "done" means

The deliverables, in priority order (full detail in `project_progress.md`):

1. A **human-annotated golden set** (~150 questions) over football news — the boring,
   hard part almost nobody does, which is exactly why it's the signal.
2. **Retrieval and generation measured separately** — recall@k / MRR / nDCG for
   retrieval; groundedness and citation accuracy for generation — so a failure names
   _which half_ broke.
3. **Ablations with a results table**: dense vs. hybrid retrieval, reranking on/off,
   fixed vs. semantic chunking. Show what helped _and what didn't_.
4. **Cost and latency per configuration**: tokens, cost/1k queries, p50/p95 latency.
5. **One honest, documented failure case** — where it breaks and why.

Stretch (only after 1–5 are solid): an **agentic layer (LangGraph)** that decides whether
to retrieve at all, reformulates weak queries, and is allowed to answer "I don't know."

**Done** is when the README can _truthfully_ state the ablation results, the abstention
rate, and the failure case — with every number regenerated by a single command. If that
paragraph can't be written honestly, the project isn't finished, no matter how much code
exists.

## 5. Domain

Football / soccer news — **top-5 European leagues + Champions League**, roughly the
2024–2026 seasons, ingested via **GDELT**. The domain is a **configuration knob** (the
GDELT query list), so the same machinery retargets to F1, cybersecurity, or anything else
without touching the core. Football was chosen for affinity: I understand it well enough
to build and judge a good golden set, and it's rich in _temporally evolving, conflicting_
stories (transfer sagas), which is the best material for RAG evaluation.

## 6. Data & copyright (a real constraint, not boilerplate)

- **Never commit third-party article text.** News bodies are the outlets' copyright. The
  repo stores URLs, IDs, embeddings, short snippets, and the _scripts to rebuild_ the
  corpus — never the bodies themselves. The SQLite DB and the HTML cache are git-ignored.
- The **one committed data artifact** is `data/golden/` — my own questions and
  annotations, not anyone's article text.
- Sources are public and licensing-safe (e.g. BBC, ESPN, The Guardian via GDELT). A
  reader who sees this reasoning written down reads it as someone who can be trusted with
  production data — that is itself worth something.
